# EMART migration report

## Migration summary

The seven static HTML entry points are represented by Next.js routes. The implementation uses Next.js 16.4.0, React 19.3.0, TypeScript 6.0.3, Tailwind CSS 4.3.3 and official shadcn Button, Input and Dialog components customized to EMART's dark theme. Versions were resolved from the package registry rather than assumed from earlier Next.js releases.

The migration preserves the original content, assets, cookie-based demo login, calculations, gauge thresholds/precision, random demo telemetry, history page size/order/accumulation, form constraints and device request contracts. Debugging mode remains the default, as requested. There is no new backend or authentication implementation.

Work proceeded through source inventory, a successfully built minimal foundation, page/interaction conversion, functional regression checks, then contrast/accessibility/UI corrections. The original source was retained through verification and then removed at the user's request.

## Architecture

```text
app/
  layout.tsx              metadata, font stack, skip link, footer
  globals.css             Tailwind v4 semantic theme and necessary control CSS
  page.tsx                login entry
  login/page.tsx
  not-found.tsx
  (application)/
    layout.tsx            navigation and main landmark
    dashboard/page.tsx
    history/page.tsx
    setting/page.tsx
    about/page.tsx
    error/page.tsx
components/
  layout/                 Navigation, Footer, PageHeading
  sections/               Dashboard, Gauges, MeterChart, Calculator,
                          DeviceEditor, History, Settings, LoginForm
  shared/                 Panel, Metric, Notice, character filter
  ui/                     shadcn Button, Input, Dialog
lib/
  device.ts               firmware transport, types and parameter construction
  energy.ts               pure calculations, gauge masking, history behavior
  utils.ts                clsx + Tailwind class merging
public/img/               original files and extracted embedded assets
tests/                    unit, browser, accessibility and device contract tests
scripts/                  original capture, responsive audit, contrast, measurements
```

All route pages and layouts are Server Components. About content, footer and headings are server-rendered. Interactive regions are client islands; no root client provider was introduced.

The animated title and endless decorative error-page glitch were removed; route metadata supplies stable titles. Context-menu blocking and global text-selection blocking were not carried forward. Original entry/meter animation effects were simplified to static rendering; control motion is optional under reduced-motion preferences. No new business workflow was added.

The existing keypress filter, native length/range validation, password fields' original text/password types and GET firmware contracts were retained even where a new product design might choose differently. The cut-off checkbox remains a local-only control because the source defines no save contract.

## Dependencies and simplicity pass

Added Next/React, Tailwind/PostCSS, TypeScript/ESLint, class utilities, two Radix primitives and Lucide for the three shadcn primitives. Development checks use Playwright and axe. Yarn remains the package manager; yarn.lock records resolved versions. Prettier was run through yarn dlx and not added as a project dependency.

Removed the shadcn CLI's redundant `cn` package and umbrella `radix-ui` import in favor of the existing local cn helper and the two specific Radix packages. No chart library, global state store, form library, server API facade, theme package or animation library was added. Legacy CSS and jQuery were removed from both runtime and source.

## Advanced Next.js features

- **Cache Components — deferred.** Every route shell already prerenders; live/device data belongs to browser subscriptions and must not become shared cached state. No measured server waterfall justifies another caching layer.
- **Partial Prefetching — deferred.** Requires Cache Components in this installed release. Measurements showed automatic navigation prefetch downloading dashboard code on About, so navigation/footer Links now use `prefetch={false}` while retaining client navigation. No URL-dependent server data justifies Partial Prefetching.
- **View Transitions — rejected for this migration.** Supported by this release, but this meter dashboard has no shared-element flow that needs them. They would add decorative motion rather than preserve a meaningful workflow.

These decisions follow the installed Next.js documentation under node_modules/next/dist/docs. Framework setup was also cross-checked against [Next.js installation](https://nextjs.org/docs/app/getting-started/installation), [Tailwind Next.js installation](https://tailwindcss.com/docs/installation/framework-guides/nextjs), and [shadcn configuration](https://ui.shadcn.com/docs/components-json).

### Measured performance

Fresh Chromium contexts, 1280px viewport, production Next server, 1.5 seconds after navigation; values below are decoded JavaScript bytes actually requested. This is a load-size comparison, not a Core Web Vitals or interaction-latency benchmark.

| Route | Original static | Next before prefetch adjustment | Final Next |
| --- | ---: | ---: | ---: |
| Login | 27,226 | 519,084 | 516,270 |
| Dashboard | 248,766 | 583,395 | 555,220 |
| History | 102,368 | 583,395 | 505,706 |
| Setting | 100,040 | 583,395 | 505,821 |
| About | 8,280 | 583,395 | 466,473 |
| Error | 8,280 | 583,395 | 466,473 |

Disabling speculative navigation/footer prefetch reduced About/Error's initially requested JavaScript by 116,922 bytes (20%). Their transferred JavaScript fell from 184,526 to 141,727 bytes. Final shared CSS is 42,751 decoded bytes versus the original 38,925. Next/React still impose a larger JavaScript baseline than the original static site; this migration does not claim a smaller overall bundle or faster runtime. The reference server sends uncompressed files while Next compresses responses, so their transfer sizes are not a fair framework comparison. Measurement JSON is retained in `.verification/measurements.json` and `.verification/measurements-before-prefetch.json`.

## Known issues and deferred work

- No physical EMART device was available. HTTP/WebSocket contracts were tested with browser-intercepted fixtures; real firmware, networking, cookie deployment and restart behavior remain unverified on hardware.
- Debug mode intentionally retains failing settings/edit/save requests when firmware endpoints are absent. It does not silently save fictional data.
- Demo login still accepts any nonempty password and uses the existing username cookie. This is preserved behavior, not production authentication. A separate authentication project would be needed before treating it as a protected hosted service.
- Debug history still generates future dates and accumulates totals on page visits; its kW labels are retained. These source quirks require a product/business decision before changing them.
- Actual screen-reader speech, Safari/Firefox, physical touch devices and deployment under a subpath were not tested. Chromium accessibility-tree/keyboard/axe checks are not a claim of full WCAG certification.
- Named skills absent from the installed skill directories (Superpowers, Ponytail, Caveman, web-design-guidelines, vercel-react-best-practices, next-dev-loop, next-bundle-optimizer, vercel-optimize) could not be executed. The supplied investigate/plan/implement/verify/review and simplicity workflow was performed directly. Installed better-accessibility, better-colors and better-ui instructions were used.

## Concise engineering review

The architecture changed; device contracts and calculations did not. Rendering/state ownership is now explicit and testable. Keyboard access, visible focus, contrast, reflow and error readability improved. Hardware integration and real authentication remain outside this migration's verified scope. Stop after the recorded checks pass; additional product behavior changes need separate requirements.
